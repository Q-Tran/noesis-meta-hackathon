Two safety rules, both tested, because automation here is one step from
amplification:
1. A step never reads output from its own wave. Otherwise one wrong Insight
   becomes a Problem, then an Idea, then committed work -- a single mistake
   converted into a structure that looks deliberate.
2. Inferences need confirmation by DEFAULT -- the opposite of ~ingest_information~,
   which writes immediately. Ingestion records what somebody said; a cascade step
   asserts something nobody said. Writes are tagged ~cascade::<step>~ so a later
   pass can tell inference from observation.

**** THE DECISION GAP IS CLOSED -- by attribution, not by fabrication
Previously no step could create a Decision, on the grounds that a Decision is a
choice somebody is accountable for. That gap was drawn around the wrong thing:
one hop carried two different jobs. PROPOSING a strategy is reasoning over
evidence, which an agent does about as well as a person. BEING ANSWERABLE for it
is not reasoning at all, and arrives only when a named person adopts it.

So ~CascadeStep~ gained ~human_attribution~: a step producing an entity somebody
must own declares the edge its confirmer has to supply, and the write is REFUSED
with ~AttributionRequired~ unless a real Person is named. That protects the
accountability directly, which frees the reasoning to be automatic.
~decisions.strategy_from_goals~ (Goal -> Decision via INTENDED_FOR, ~MADE_BY~,
cap 5) is the result. Three routes share one validation path in
~knowledge_bases/decisions/strategy.py~: an agent proposes and a human confirms,
a human authors directly, or a human steers the agent first
(~StrategyGuidance~, per-run and deliberately not persisted).

The old test was REWRITTEN over labels rather than deleted, so any FUTURE step
producing an owned entity is caught the day it is written.

**** THE LAST TWO ARROWS: two trigger kinds, not one
The two remaining hops looked alike and are not, and the ontology says so: all
eight ~Code*~ labels are ~extractable=False~, so no reasoner may produce one.

- ARCHITECTURE is reasoned. ~architecture.structure_from_decisions~ (Decision ->
  Architecture/Component/Interface via AFFECTS, steerable, cap 12) records the
  structure a decision COMMITS TO. This is the FORWARD direction and it is why the
  hop has to exist: indexing a checkout reports the components that ARE there and
  can never recover why a boundary was drawn where it was, because that is a
  decision and decisions are not in the source. It supplies exactly the AFFECTS
  edge that leaves a cascade-proposed Decision ~incomplete~.
- DEVELOPMENT is measured, not reasoned -- so "built when a codebase is opened" is
  the right mechanism, and it is not a ~CascadeStep~ at all, because its trigger
  is a filesystem event rather than a graph entity.
  ~knowledge_bases/development/open_codebase.py~: ~on_open~ indexes a checkout if
  the graph lacks it and is safe to call on every open (an already-current repo
  costs one query and indexes nothing). Four distinguishable no-op outcomes, and
  failures are returned as data because this runs when a person opens a file.
- ~on_generate~ is the "create rather than ingest" case: for a codebase Noesis
  produced, the design already exists, so indexing also writes ~CATALOGS~.
  That edge was DECLARED and never written by anything --
  ~architectural_rationale()~ had always reported ~rationale_recorded: False~.
  It is written by the indexer and not by a reasoner because asserting "this
  architecture is realised by that checkout" is a claim about a real directory.

**** THREAD LIMITING: done, as a correctness feature
~knowledge_bases/project_management/task_runner.py~. ~max_threads~ is
keyword-required with NO default and no unlimited setting, because the bound is
not a performance knob: an unattended runner that starts every ready task at once
exhausts whatever the tasks themselves need, produces failures that depend on what
happened to be running beside them, and makes the blast radius of a bad task list
unbounded.

Readiness is a graph question using both edges for their own meanings --
~DEPENDS_ON~ blocks only while the prerequisite is unfinished, ~BLOCKED_BY~ blocks
by existing. Runs proceed in bounded ROUNDS, since finishing a task is what makes
its dependents ready. A failing task is recorded ~blocked~ (the enum has no
~failed~) and does not stop the run; the report separates what completed, what
failed, and what the run never reached. Only the read-only ~list_ready_tasks~ is
exposed as a tool: ~run_tasks~ performs side effects that declining to confirm
cannot undo.

THE ASYMMETRY THAT GOVERNS ALL OF THIS: an invalid triplet is loud (it comes back

produces no rejection at all. So every scoping optimization trades tokens for a
risk that leaves no trace. Detection needs a shadow audit (re-extract 1-5% of
documents with the full prompt and diff) which does not exist yet.
