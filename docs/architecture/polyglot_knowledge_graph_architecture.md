# Enterprise Knowledge Graph Architecture: "Digital God" Scale

## Executive Summary
This document outlines the architecture for an enterprise-scale Knowledge Graph designed to ingest, process, and analyze massive volumes of internal communications (emails, Teams messages, documents) to generate actionable business insights. The system is designed to run securely within a Private Cloud VPC and handle horizontal scaling into the billions of nodes and vectors.

## Core Architectural Pillars
The solution relies on a Decoupled (Polyglot) approach, separating the storage of graph relationships from semantic vector embeddings to optimize performance and control infrastructure costs.

### 1. Provenance Layer (The Nervous System)
*   **Technology:** Apache Kafka
*   **Role:** An indestructible, high-throughput message broker that buffers all incoming data streams in real-time, and the point of entry where every fact is first tagged with where it came from.
*   **Functionality:** Source systems (Exchange, Teams) act as Producers, dropping raw messages onto designated Kafka Topics (e.g., `raw-emails`, `teams-messages`), each carrying `source_name`/`source_type`/`url` metadata. This decouples source systems from the processing layer and prevents database overload during traffic spikes, ensuring zero data loss. Downstream, the Processing Layer (`extract.py`/`worker.py`) turns that per-message metadata into a `SourceNode` and links every entity it extracts back to it via `(:Entity)-[:FOUND_IN {role}]->(:SourceNode)` — the same graph-native epistemology layer used for structured catalog/metric provenance (see [provenance.md](provenance.md)). The message broker is where a fact enters the system; the `SourceNode`/`FOUND_IN` graph is where that fact's origin is preserved and made traceable.

### 2. Processing Layer (The Workers)
*   **Technology:** Stateless CPU-based microservices (Python/Go) consuming Kafka topics.
*   **Role:** The intelligence engine responsible for data extraction and embedding generation.
*   **Functionality:**
    *   **LLM Extraction:** Calls the internal Company LLM API to extract entities, sentiment, and business insights from the raw text. (Offloads expensive GPU compute).
    *   **Embedding Generation:** Generates lightweight vector embeddings representing the semantic meaning of the content/insights using local CPU compute.

### 3. Graph Database Layer (The Relational Brain)
*   **Technology:** Neo4j (Enterprise)
*   **Role:** The Source of Truth for *Relationships* and *Identity*.
*   **Functionality:** Stores the structural connections (e.g., `(User)-[:SENT]->(Message)-[:MENTIONS]->(Project)`). Crucially, Neo4j generates a unique `Node_ID` (UUID) for every piece of content and insight created. Because Neo4j natively pages to disk, it can manage terabytes of relational data without prohibitive RAM costs.

### 4. Vector Database Layer (The Semantic Brain)
*   **Technology:** Milvus (configured with DiskANN)
*   **Role:** The Source of Truth for *Semantic Meaning*.
*   **Functionality:** Stores the billions of vector embeddings. By utilizing the DiskANN algorithm, Milvus stores the vast majority of the vector index on fast SSDs (e.g., AWS EBS gp3) rather than in RAM. Each vector is stored alongside the corresponding `Node_ID` generated by Neo4j.

## Dual-Write Consistency and Query Flow

### Integration Point (The Bridge)
The processing workers orchestrate a dual-write mechanism. When a new message is processed:
1.  The worker writes the structural data to Neo4j and receives the generated `Node_ID`.
2.  The worker writes the generated vector embedding to Milvus, inserting the Neo4j `Node_ID` as scalar metadata attached to the vector.

### Query Execution (Semantic -> Relational)
When a user asks a complex question (e.g., *"Find discussions about Project X delays among senior management"*):
1.  **Vector Search:** The query is embedded, and Milvus is searched using DiskANN to find the top $N$ semantically relevant vectors. Milvus returns a list of Neo4j `Node_IDs`.
2.  **Graph Traversal:** The list of `Node_IDs` is passed into Neo4j via a Cypher query. Neo4j filters the results based on complex relational rules (e.g., `WHERE sender belongs_to 'Senior Management'`).

## Infrastructure Footprint (Private VPC)
*   **Compute:** CPU-optimized EC2 instances/Pods for Processing Workers.
*   **Messaging:** Managed or self-hosted Kafka Cluster.
*   **Graph Storage:** Neo4j cluster (with read replicas for scale).
*   **Vector Storage:** Distributed Milvus cluster utilizing SSD/NVMe backed storage for DiskANN indexes.
*   **AI Compute:** Internal Company API (LLM inference) + CPU (Embedding generation).
